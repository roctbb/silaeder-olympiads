# Архитектура сервиса

## Границы доступа

Каталог, календарь, подробные карточки, материалы, число добавивших олимпиаду и
добровольно опубликованные имена доступны без авторизации. Публичное API
возвращает только редакции со статусом `published`.

Вход через ЛК «Силаэдр» нужен для локального класса, личного плана, настройки
напоминаний и результатов по этапам. Пользовательские операции записи требуют и
server-side сессию, и `X-CSRF-Token`: анонимный клиент получает `401`, клиент с
неверным CSRF — `403`. Административный интерфейс защищён отдельной локальной
учётной записью и не наследует роль из CRM. После admin login идентификатор
server-side сессии ротируется; выход и все операции записи каталога требуют
отдельный CSRF-токен из ответа admin session.

## Компоненты

```text
                       ┌───────────────────────────┐
                       │ ЛК «Силаэдр»              │
                       │ OIDC + notifications API  │
                       └──────────▲───────▲────────┘
                                  │       │ HTTP Basic + Idempotency-Key
                     OIDC code    │       │
                                  │       │
┌───────────────┐  JSON/session  ┌┴───────┴──────────────┐
│ Vue 3         ├───────────────►│ Flask API             │
│ Bootstrap 5   │                │ Authlib / SQLAlchemy   │
└───────────────┘                └───────┬─────────┬──────┘
                                        │         │
                                  ┌─────▼───┐ ┌───▼──────────────┐
                                  │ Redis   │ │ PostgreSQL       │
                                  │ session │ │ catalog, plans,  │
                                  │ broker  │ │ progress, outbox │
                                  └─────┬───┘ └───▲──────────────┘
                                        │         │
                                  ┌─────▼─────────┴──────┐
                                  │ Celery beat + worker │
                                  └──────────────────────┘
```

Redis разделён логически: broker использует database 0, result backend — 1,
server-side Flask sessions — 2. PostgreSQL и Redis в Compose не публикуют порты
наружу.

## Каталог и стабильная идентичность этапов

- `Olympiad` — стабильная сущность «соревнование + профиль».
- Публичное `direction` — вычисляемая навигационная таксономия над точным
  `Olympiad.profile`: один профиль может иметь несколько направлений, но новых
  сущностей и объединения карточек в базе не создаётся.
- `OlympiadEdition` — данные конкретного учебного года: статус публикации,
  принадлежность проекту перечня, числовые классы либо текстовые условия участия
  `eligibility_notes`, результат и дата проверки регистрации, льготы и источники.
- `Stage` — регистрация или тур с датами, точностью, подтверждением, стабильным
  `key` и признаком `is_active`.
- `Material` — внешняя ссылка на задания, решения, видео, курс или архив.
- `Benefit` и `University` — правило льготы для конкретного вуза и года приёма.
- `SourceLink` — происхождение данных, год источника и дата проверки.

`Stage.key` создаётся сборщиком детерминированно и уникален внутри редакции.
Импорт сопоставляет этапы сначала по ключу, поэтому вставка нового тура перед
финалом или изменение позиции не меняет идентичность финала. Этап, исчезнувший из
нового снимка, получает `is_active=false`: публичный календарь его больше не
показывает, но связанный пользовательский результат остаётся доступен в истории.

`flask import-catalog SOURCE` выполняет идемпотентный upsert переданных записей.
Флаг `--sync` означает полный снимок только для учебных годов, присутствующих в
файле: отсутствующие редакции архивируются, а не удаляются. Олимпиаду нельзя
удалить из админки, пока на неё существует хотя бы один личный план.

## OIDC и локальный пользователь

Backend использует discovery от `CRM_OIDC_ISSUER` и Authlib Authorization Code
Flow. Authlib создаёт и проверяет `state`, `nonce`, PKCE verifier/challenge
`S256`, подпись и стандартные claims ID token. Callback и post-logout callback
строятся только из фиксированного `APP_BASE_URL`.

`User` связан с CRM уникальной парой `(oidc_issuer, oidc_subject)`. Email,
отображаемое имя, роль и тип объекта обновляются при каждом входе; связывания по
email или числовому `object_id` нет. Класс `grade` хранится локально с ограничением
5–11, потому что текущий `userinfo` CRM его не содержит.

После callback access token используется для свежего `userinfo` и не передаётся
frontend. Локальная сессия и ID token для RP-Initiated Logout находятся в Redis;
cookie содержит только непрозрачный идентификатор сессии. Для production нужны
`HttpOnly`, `SameSite=Lax` и `Secure`. После входа идентификатор сессии ротируется,
а logout URL принимается только с origin настроенного OIDC issuer.

Точный пользовательский контракт приведён в
[документации персонализации](personalization-api.md).

## Личный план и приватность

- `UserOlympiadPlan` уникален по `(user_id, edition_id)` и хранит статус
  `planned`, `registered`, `participating` или `completed`.
- `is_name_public=false` по умолчанию. Счётчик участников учитывает все планы, а
  публичный список имён — только явно включивших публикацию для этой олимпиады.
- `reminders_enabled` и `reminder_days_before` задают локальное расписание;
  значение по умолчанию — `[7, 1]`.
- `UserStageProgress` уникален по `(plan_id, stage_id)` и хранит `participated`,
  nullable `advanced` и текст результата. При `participated=false` остальные
  поля канонически сбрасываются в `null`.

Удаление плана каскадно удаляет только принадлежащие ему прогресс и будущие
dispatch-записи. Оно не затрагивает каталог. Публичные ответы никогда не содержат
OIDC subject, email или результаты другого пользователя.

Архивирование редакции не превращает личные данные в недоступные: владелец видит
архивный план и прежний прогресс в `GET /api/v1/me/plan`, может отозвать публикацию
имени, выключить напоминания или удалить план. Архивные этапы не входят в блок
ближайших событий, а публичные catalog/detail/planning endpoints архивную редакцию
не возвращают.

## Durable-напоминания через ЛК

В Compose работают два независимых процесса:

1. Celery beat ежедневно в 07:00 `Europe/Moscow` запускает `reminders.scan`.
2. Scanner выбирает активные планы и только активные этапы с подтверждённой датой.
3. Для каждого настроенного порога он заранее сохраняет `ReminderDispatch` в
   PostgreSQL. Уникальность `(plan, stage, event_on, days_before)` не даёт создать
   дубликат.
4. Due dispatch переводится в `processing` под row lock и отправляется worker-ом
   в `CRM_NOTIFICATION_URL` с HTTP Basic и сохранённым `Idempotency-Key`.
5. Ответ `200` или `202` фиксируется как `sent`; это означает принятие ЛК, а не
   доказательство доставки в конкретный канал.
6. Таймаут, сетевая ошибка, `429` и `5xx` переводят запись в `retry`. Задержка —
   exponential backoff с jitter и учётом `Retry-After`. По умолчанию разрешено
   не больше 12 попыток и не дольше одного дня после `scheduled_for`; исчерпание
   попыток даёт `permanent_failed`, истёкшее окно — `cancelled`.
7. Остальные `4xx` становятся `permanent_failed`. Изменённый/снятый этап,
   выключенное напоминание или завершённый план дают `cancelled`.

Перед каждым повтором проверяются неизменность события, сохранённого payload и
его SHA-256. `processing`-запись со старой lease может быть безопасно подобрана
после падения worker. Идемпотентный ключ и тело запроса повторно используются без
изменений. Celery подтверждает задачу после выполнения (`acks_late`), возвращает
её в очередь при потере worker и забирает не больше одной задачи наперёд.

ЛК получает `recipient_sub`, заголовок, текст и URL карточки, затем самостоятельно
рассылает уведомление по настроенным пользователем email/Telegram-каналам. Отдельный
access token для notification API не используется; право `can_send_notifications`
назначается конфиденциальному OIDC-клиенту в CRM.

## Локальная и production-топология

Локально Vue работает на `http://localhost:5188`, Flask — на
`http://localhost:5050`. В CRM должны быть зарегистрированы точные URI:

```text
http://localhost:5050/auth/crm/callback
http://localhost:5050/auth/crm/logout/callback
```

CRM разрешает HTTP только для loopback-host, поэтому OIDC нельзя проверять через
LAN-IP. Публичный режим не требует OIDC credentials.

В production рекомендуется один внешний HTTPS-origin. Reverse proxy отправляет
`/api/*` и `/auth/crm/*` в Flask, остальные маршруты — в Vue. Например, при
`APP_BASE_URL=https://olympiads.example.ru` в CRM регистрируются:

```text
https://olympiads.example.ru/auth/crm/callback
https://olympiads.example.ru/auth/crm/logout/callback
```

Обязательны постоянный `SECRET_KEY` не короче 32 символов,
`SESSION_COOKIE_SECURE=true`, общий Redis для всех API-инстансов, production
credentials CRM, минимум один worker и ровно один beat. Production без стойкого
секрета завершается до инициализации приложения; небезопасный fallback разрешён
только явно в локальном Compose.

Миграции выполняет отдельный одноразовый job до rollout API/worker/beat, чтобы
реплики не конкурировали за Alembic lock. `/api/live` проверяет процесс, а
`/api/health` — готовность PostgreSQL и Redis. Попытки
`POST /api/admin/session` должны ограничиваться rate limit на reverse proxy,
общем для всех Gunicorn worker. Полный набор переменных и порядок запуска
приведены в [README](../README.md#production-настройка).
